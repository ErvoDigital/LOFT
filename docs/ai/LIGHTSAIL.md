# OpenClaw on AWS Lightsail

This deployment runs the assistant's Docker container on a persistent Linux VPS. The website and LOFT API can remain on their current hosts. The connection is:

`Browser -> authenticated LOFT API -> HTTPS on Lightsail -> OpenClaw -> OpenRouter`

The website calls the gateway through the LOFT backend. It does not access the Docker Engine API. No AWS access key, Docker socket, database credentials or LOFT JWT secret is needed on the gateway host.

## Files and commands

- `infra/openclaw/compose.yml`: pinned OpenClaw image, restart policy, persistent state and mounted LOFT speech plugin.
- `infra/openclaw/compose.lightsail.yml`: adds Caddy with persistent TLS certificate storage.
- `infra/openclaw/Caddyfile`: exposes only `POST /v1/responses`, `POST /v1/audio/transcriptions`, `POST /v1/audio/speech` and `GET /v1/models`; other HTTPS paths return 404. OpenClaw checks bearer authentication on all endpoints. No gateway UI or WebSocket control endpoint is exposed.
- `infra/openclaw/plugins/loft-speech`: native OpenClaw plugin that handles bounded audio uploads and speech playback using the same host-side OpenRouter key as reasoning.
- `infra/openclaw/.env.lightsail.example`: gateway-only settings template. Setup creates an ignored `.env.lightsail` with a random token.

Run the `ai:lightsail:*` commands **on the VPS**, from this repository's root. They manage Docker on the machine where they are run; they do not provision AWS resources or deploy over SSH. Local development continues to use the existing `ai:*` commands and `server/.env`.

## Prepare the host

1. Create a Linux Lightsail instance with a supported Ubuntu LTS image. Use an x86_64 instance for the initial deployment; the pinned gateway image must support the host architecture. Choose memory/disk capacity based on gateway usage and monitor it.
2. Attach a [Lightsail static IPv4 address](https://docs.aws.amazon.com/lightsail/latest/userguide/lightsail-create-static-ip.html). Point an `A` record such as `ai.example.com` to it. Only add an `AAAA` record if IPv6 routing and firewall rules are also configured.
3. Configure the [Lightsail firewall](https://docs.aws.amazon.com/lightsail/latest/userguide/understanding-firewall-and-port-mappings-in-amazon-lightsail.html): SSH TCP 22 from your administrative IP, HTTP TCP 80 for certificate issuance/redirects, HTTPS TCP 443 for the LOFT API. If the API has stable outbound IPs, restrict 443 to those IPs. Port 80 allows certificate issuance with the HTTP challenge; Caddy also supports the TLS challenge on 443. Do not allow public TCP 18789 or Docker API ports 2375/2376. Review IPv6 rules separately if enabled. Lightsail's public firewall does not filter private-IP traffic.
4. Install [Docker Engine and its Compose plugin](https://docs.docker.com/engine/install/ubuntu/), plus Node.js 22.16+ and npm for the helper scripts. Give the deployment user permission to use Docker.
5. Check out this repository on the VPS. The helper only needs its `dotenv` dependency; you can install it without running Prisma's install hook using `npm ci --workspace server --include-workspace-root --ignore-scripts`. No server database configuration is needed to run the gateway helpers.

Caddy obtains and renews certificates for the configured domain when DNS and networking are ready. See [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https). The raw gateway stays on `127.0.0.1:18789` for host-local checks, while Caddy reaches it on the Docker network. The Docker Engine itself stays local to the VPS.

## Configure and start the gateway

```bash
npm run ai:lightsail:setup
chmod 600 infra/openclaw/.env.lightsail
```

Edit that file on the VPS:

```dotenv
OPENCLAW_DOMAIN="ai.example.com"
OPENCLAW_GATEWAY_TOKEN="<generated by setup; keep it>"
OPENROUTER_API_KEY="<your OpenRouter key>"
OPENROUTER_STT_MODEL="openai/gpt-4o-mini-transcribe"
OPENROUTER_TTS_MODEL="google/gemini-3.1-flash-tts-preview"
OPENROUTER_TTS_VOICE="Kore"
```

`OPENCLAW_DOMAIN` is a hostname only, with no `https://`, port or path. Setup preserves existing values and never prints tokens. The key belongs on this host, and the gateway token must also be configured on the LOFT backend.

```bash
npm run ai:lightsail:config   # Compose validation; does not print resolved secrets
npm run ai:lightsail:start
npm run ai:lightsail:check    # HTTPS + authentication + expected model list, no paid inference
npm run ai:lightsail:logs
```

The check does not require a database. An authenticated model list verifies connectivity, not OpenRouter credits or inference. DNS/certificate issuance may take time after first startup; retry the check once Caddy logs show that HTTPS is ready. Requests with missing/incorrect bearer tokens must be rejected by the gateway. An unauthenticated request to `https://ai.example.com/v1/models` should return 401; `/` should return 404 over HTTPS.

## Upgrade an existing gateway for audio

Update the VPS checkout with the new `plugins/loft-speech` directory, `openclaw.json`, Compose files and `Caddyfile`. Keep the existing gateway token and OpenRouter key. Run these commands from the checkout root on the VPS:

```bash
npm run ai:lightsail:setup   # Adds missing speech defaults; preserves existing credentials.
npm run ai:lightsail:config
npm run ai:lightsail:start
docker compose --env-file infra/openclaw/.env.lightsail -f infra/openclaw/compose.yml -f infra/openclaw/compose.lightsail.yml restart openclaw
docker compose --env-file infra/openclaw/.env.lightsail -f infra/openclaw/compose.yml -f infra/openclaw/compose.lightsail.yml exec -T caddy caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
npm run ai:lightsail:check
```

Restarting OpenClaw loads the updated plugin code even when the existing container did not need recreation. Reloading Caddy activates the new speech routes on existing proxy containers. If a custom `--settings-file` is used, substitute that file for `.env.lightsail` in all commands. Deploy/restart the LOFT backend with the speech service change, then test a short microphone clip and assistant playback. Text and both speech operations now use the VPS's `OPENROUTER_API_KEY`. Provider credits are still required.

## Connect the LOFT backend

Set these **server-side** environment variables on the host running the LOFT API:

```dotenv
OPENCLAW_GATEWAY_URL="https://ai.example.com"
OPENCLAW_GATEWAY_TOKEN="<same token as the VPS>"
```

Do not append `/v1` to the URL. Do not put either value in a `VITE_` variable. A remote backend does not need `OPENROUTER_API_KEY`; remove that key there after moving it to the gateway. Restart/redeploy the LOFT API to load these settings. No frontend URL or CORS change is needed because the browser continues calling the authenticated LOFT API.

Run `npm run ai:check` from the backend environment to verify the actual route from that host. It reads `server/.env` when present, with exported environment variables taking precedence. It also works with exported variables and no `.env` file. Configure the backend/proxy's request timeout to accommodate the assistant's existing 90-second gateway budget plus database/tool work; serverless host limits may require a different API host.

Then send a message in the website and confirm a task/meeting in a test workspace. `/api/assistant/status` indicates that a token is configured; it does not probe gateway health.

## Operations

`npm run ai:lightsail:stop` stops both services without deleting their volumes. `npm run ai:lightsail:start` recreates services as needed. Keep the gateway state volume and Caddy certificate volumes backed up; gateway state includes conversation transcripts. Keep using the same checkout location/project name so Compose reuses those volumes. Avoid `docker compose down -v` unless you intend to erase them.

For another secrets-file location, append `-- --settings-file /absolute/path/gateway.env` to a helper command. Set the same override for setup, start, check, stop and logs. Exported environment values override the file for checks and Compose operations; remove stale exported values before switching configurations.

Rotate the gateway token on both the VPS and backend, recreate the gateway with `ai:lightsail:start`, and restart the backend. Never commit/share the filled secrets file or unredacted logs. Keep public HTTPS limited to the backend's outbound IPs when possible. If your backend lacks stable egress, this configuration uses TLS plus bearer authentication; use a private tunnel/network or an egress proxy if you require IP restrictions. Do not enable OpenClaw's trusted-proxy authentication for this setup.

The gateway image remains pinned by digest; Caddy is pinned to a release tag. Update deliberately and repeat the connectivity and assistant tests. This repository does not provision an AWS instance, configure DNS/firewalls automatically, or deploy the website itself.

## Repository verification

Run `npm run ai:test` for the helper and assistant contract tests, and `npm run build` for the website. These tests use temporary settings and mock gateways/databases; they do not provision AWS resources or spend OpenRouter credits. `ai:lightsail:config` validates Compose without starting Docker containers. Caddy's configuration can also be validated on the VPS with `docker compose --env-file infra/openclaw/.env.lightsail -f infra/openclaw/compose.yml -f infra/openclaw/compose.lightsail.yml run --rm --no-deps caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile`.
